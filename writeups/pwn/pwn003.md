# PWN#003 — Notes Vault (UAF + freelist poisoning + system)

- **Auteur :** Le_Geek
- **Cible :** `<HOST>:<PORT>` (Notes Vault, ELF x86-64 PIE)
- **Catégorie :** pwn
- **Flag :** `CTF{REDACTED}` (voir regle de non-persistance des flags)
- **Fichiers fournis :** binaire ELF x86-64 PIE, non strippe, 21864 octets

## Contexte

Service de notes interactif avec menu : Add, Free, Edit, View. Le binaire est un ELF x86-64 PIE non strippe. Aucune libc n'est fournie, mais le service distant utilise la meme glibc 2.42-13 que les challenges precedents.

Le binaire contient un allocateur de pool personnalise avec des fonctions `palloc` et `pfree` ecrites a la main, et une freelist a pointeur encode (mangle).

## Reconnaissance

### Protections

| Protection   | Etat                          |
|---|---|
| Canary       | Actif                         |
| NX           | Actif                         |
| RELRO        | Full                          |
| PIE          | Actif                         |
| Symboles     | Presents (non strippe)        |

### Fuite PIE

Au demarrage, le service affiche une adresse de `main` dans un message de debug. L'offset de `main` etant `0x1af8`, la base PIE se calcule par `main_leak - 0x1af8`.

### Allocateur de pool

Les allocations de taille 32 sont servies par un pool personnalise avec une freelist. Le pointeur suivant dans la freelist est encode par la fonction `mangle` :

```
mangle(ptr, node) = ptr XOR rol(node, 13)
```

Lorsqu'un seul chunk est dans la freelist, le pointeur encode se decode simplement par `ror(encoded, 13)`, car `ptr = 0` (fin de liste) :

```
mangle(0, chunk) = 0 XOR rol(chunk, 13) = rol(chunk, 13)
```

### Structure d'une note

Chaque note contient :
- Un pointeur de formatage (`fmt`) : fonction appelee lors de `view_note`.
- Un pointeur de contenu (`content`) : argument passe a la fonction de formatage.

`view_note` execute : `call [note->fmt](rdi = note->content)`.

## Vulnerabilite

### Use-After-Free

La fonction `free_note` libere le chunk de la note mais **ne remet jamais `notes[idx]` a NULL**. Apres `Free`, les operations `Edit` et `View` restent possibles sur la note liberee.

### Enchainement des primitifs

1. **View apres Free** : lire le chunk libere revele le pointeur freelist encode, ce qui donne l'adresse du chunk par `ror(encoded, 13)`.
2. **Edit apres Free** : ecrire dans le chunk libere permet de modifier le pointeur freelist, donc d'empoisonner la freelist pour rediriger la prochaine allocation vers une adresse arbitraire.
3. **Callback de formatage** : `view_note` appelle `[note->fmt](note->content)`, ce qui donne un controle de `rip` et de `rdi` une fois les metadonnees de la note ecrasees.

## Exploitation

### Etape 1 — Fuite du heap et empoisonnement de la freelist

1. Creer la note 0 (taille 32).
2. Liberer la note 0 (`Free(0)`).
3. Lire la note 0 (`View(0)`) : le chunk libere contient `mangle(0, chunk) = rol(chunk, 13)`. Decoder par `ror(encoded, 13)` pour obtenir l'adresse du chunk.
4. Editer la note 0 (`Edit(0)`) : ecrire un pointeur encode qui redirige la freelist vers les metadonnees de la note 1 :

```
target       = PIE_base + 0x40e0 + 24   (metadonnees de la note 1)
encoded_next = target XOR rol(chunk, 13)
```

5. Deux allocations suivantes :
   - La premiere retourne le chunk original.
   - La deuxieme retourne la cible empoisonnee (metadonnees de la note 1).

### Etape 2 — Fuite libc via puts@GOT

La deuxieme allocation ecrit dans les metadonnees de la note 1 :
- `fmt` = `puts@PLT` (adresse calculee via la base PIE).
- `content` = `puts@GOT` (adresse calculee via la base PIE).

`View(1)` appelle alors `puts(puts@GOT)`, ce qui affiche l'adresse resolue de `puts` en libc.

```
libc_base = puts_leak - 0x82060
```

L'offset `0x82060` correspond a `puts` dans la glibc 2.42-13 identifiee sur le service distant. L'alignement page a ete verifie.

### Etape 3 — Appel de system("/bin/sh")

Par le meme mecanisme d'empoisonnement des metadonnees :
- `fmt` = `system` (`libc_base + 0x54790`).
- `content` = adresse du chunk controle contenant la commande.

Le contenu du chunk est prepare avec une commande de lecture du flag. `View(1)` declenche `system(commande)` et le flag apparait dans la sortie.

### Flag

Le flag est stocke dans la variable d'environnement `FLAG=` du processus distant.

## Resultat

Shell obtenu via `system()`. Le flag a ete lu et soumis avec succes.

```
CTF{REDACTED}
```

## Pieges rencontres

- **Encodage `mangle`** : le pointeur freelist est encode par `XOR rol(node, 13)`. Oublier la rotation rend l'empoisonnement inoperant. Verifier avec un seul chunk dans la freelist (cas simple ou `ptr = 0`).
- **Freelist a un seul element** : le decodage par `ror` ne fonctionne simplement que quand le chunk est seul dans la freelist (le suivant est `NULL`). Avec plusieurs chunks, il faut connaitre le pointeur suivant pour decoder.
- **Offset du pool** : les metadonnees des notes sont a `PIE_base + 0x40e0 + 24`. Un decalage meme d'un octet dans l'adresse cible provoque une corruption silencieuse.
- **Alignement libc** : l'offset de `puts` (`0x82060`) et de `system` (`0x54790`) doivent etre verifies sur la libc distante. La libc locale peut differer.

## Lecons

1. **UAF = primitif de lecture + ecriture** : un use-after-free qui laisse le pointeur dans le tableau donne simultanement une lecture (fuite du chunk) et une ecriture (empoisonnement de la freelist).
2. **Allocateurs personnalises** : les allocateurs de pool avec freelist encodee ajoutent une couche de protection, mais celle-ci tombe des qu'on connait l'adresse du chunk (obtenue par la fuite UAF elle-meme).
3. **Callbacks stockes en memoire** : un pointeur de fonction (`fmt`) stocke a cote des donnees utilisateur est un vecteur classique de RIP control. La combinaison UAF + callback = execution arbitraire.
4. **Un seul exploit, deux etapes** : la meme technique (empoisonnement freelist + callback) sert d'abord a fuiter libc, puis a appeler `system`. La reutilisation du primitif reduit la complexite.
