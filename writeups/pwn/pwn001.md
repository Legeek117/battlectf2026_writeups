# PWN#001 — Vault Terminal (oracle memoire + seccomp bypass)

- **Auteur :** Le_Geek
- **Cible :** `<HOST>:<PORT>` (Vault Terminal, ELF x86-64)
- **Catégorie :** pwn
- **Flag :** `CTF{REDACTED}` (voir regle de non-persistance des flags)
- **Fichiers fournis :** binaire ELF x86-64 (non-PIE)

## Contexte

Premier challenge de la serie Vault Terminal. Le binaire est un ELF x86-64 non-PIE, avec Full RELRO, canary et NX actifs. L'enonce indique d'obtenir un shell sur l'hote distant et de lire le flag — mais c'est une fausse piste deliberee.

## Reconnaissance

### Protections

| Protection   | Etat                |
|---|---|
| Canary       | Actif               |
| NX           | Actif               |
| RELRO        | Full                |
| PIE          | Desactive           |
| seccomp      | Actif (voir ci-dessous) |

### Seccomp

L'analyse du filtre seccomp revele que les syscalls `execve` et `openat` sont bloques. Les syscalls `read`, `write`, et `getpid` (entre autres) restent autorises. Il est donc **impossible d'obtenir un shell** — l'enonce est une fausse piste deliberee.

### Difference binaire local / distant

Le binaire distant differe du binaire fourni par un decalage de `+0x10` sur certains offsets. Ce decalage doit etre identifie par empreinte a distance (fingerprinting) avant de pouvoir exploiter le service correctement. Les offsets du canary, du retour et des gadgets doivent etre ajustes en consequence.

### Layout de pile

- Buffer de nom : 72 octets.
- Lecture du nom : 73 octets dans un buffer de 72 octets (off-by-one sur le canary LSB).
- Canary a l'offset `0x48`, adresse de retour a `0x58`.

### libc distante

Identification : **Debian GLIBC 2.42-13**. L'offset de `puts` dans la GOT permet de calculer la base libc une fois la fuite obtenue.

### Emplacement du flag

Le flag est stocke dans la variable d'environnement `FLAG=`, et non dans un fichier. Il faut donc lire la memoire du processus pour localiser le pointeur `environ` et parcourir la table des variables d'environnement.

## Vulnerabilite

### Fuite du canary

Le nom est lu avec 73 octets dans un buffer de 72 octets. Le 73e octet ecrase le LSB nul du canary. L'affichage subsequent par `printf("%s", buf)` sans terminaison NUL provoque la fuite des 7 octets superieurs du canary.

Canary reconstruit : `b"\x00" + leak[72:79]`.

### Debordement du message

Le message deborde le buffer de 72 octets, permettant d'ecrire au-dela du canary et de l'adresse de retour pour monter une chaine ROP.

## Exploitation

### Strategie : oracle de lecture memoire

Puisque `execve` est bloque par seccomp, la strategie est de construire un oracle de lecture memoire via `write(1, addr, n)` :

1. **Fuite libc via GOT** : une chaine ROP appelle `puts(puts@GOT)`. Comme le binaire est non-PIE et Full RELRO, l'entree GOT de `puts` contient l'adresse resolue de `puts` en libc. La base libc est calculee par soustraction de l'offset connu.

2. **Lecture de `environ`** : avec la base libc, localiser le symbole `environ` (pointeur vers la table des variables d'environnement du processus). Utiliser `write(1, environ, 8)` pour lire le pointeur, puis `write(1, *environ, N)` pour parcourir la table `char **environ`.

3. **Extraction du flag** : scanner les chaines de la table d'environnement pour trouver celle qui commence par `FLAG=`.

### Chaine ROP (deux etapes)

**Etape 1 — Fuite libc :**

```
[0..71]   padding
[72..79]  canary
[80..87]  saved rbp (junk)
[88..]    pop rdi; ret -> puts@GOT -> puts@plt -> retour boucle
```

Resultat : l'adresse resolue de `puts` est affichee. `libc_base = puts_leak - puts_offset`.

**Etape 2 — Lecture de la table d'environnement :**

```
[88..]    pop rdi -> 1 (fd stdout)
          pop rsi -> environ_ptr
          pop rdx -> taille
          syscall write
```

La chaine parcourt `environ` en suivant les pointeurs jusqu'a trouver `FLAG=...`.

### Retour a la boucle

Le gadget `pop rax; xchg rdi, rax; ret` identifie dans le binaire permet de charger `rdi` sans `pop rdi` direct. Le retour a l'adresse de la boucle principale (`0x4012fc` + ajustement `+0x10` pour le distant) permet de relancer l'exploitation pour l'etape 2 apres la fuite libc.

## Resultat

Le flag a ete extrait de la variable d'environnement `FLAG=` du processus distant et soumis avec succes.

```
FLAG=CTF{REDACTED}
```

## Pieges rencontres

- **"Get a shell" est un piege** : l'enonce dit d'obtenir un shell, mais seccomp bloque `execve`. L'approche correcte est un oracle de lecture memoire.
- **Decalage binaire local/distant** : le binaire fourni differe du distant de `+0x10`. Sans fingerprinting, les offsets sont faux et l'exploitation echoue silencieusement.
- **Flag dans l'environnement** : chercher un fichier `/flag` ou `/flag.txt` ne donne rien. Le flag est dans `FLAG=` de l'environnement du processus.
- **Full RELRO** : la GOT n'est pas ecrasable, mais reste lisible pour la fuite libc via `puts`.

## Lecons

1. **Toujours analyser seccomp** : l'enonce d'un challenge peut etre deliberement trompeur. Le filtre seccomp est la verite ; l'enonce est de la narration.
2. **Fingerprinter le binaire distant** : ne jamais supposer que le binaire fourni est identique au distant. Un decalage meme faible (`+0x10`) invalide toute la chaine ROP.
3. **Penser au-dela du shell** : `write(1, addr, n)` est un primitif de lecture memoire suffisant pour extraire un flag depuis n'importe quel emplacement memoire, y compris les variables d'environnement.
4. **`environ` de la libc** : le symbole `environ` dans la libc pointe vers la table des variables d'environnement. C'est un vecteur d'attaque sous-utilise quand `execve` est bloque.
